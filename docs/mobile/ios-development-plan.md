# iOS development and test plan with a temporary Mac

Status: implementation in progress for [iOS issue #51](https://github.com/KatInBroek/shuttli/issues/51). Product behavior and acceptance remain in the [mobile feature specification](feature-spec.md) and [iOS specification](ios.md); shared protocol and SDK prerequisites belong to [issue #50](https://github.com/KatInBroek/shuttli/issues/50). A buildable app and real-device behavior require separate verification.

## Use each environment for what it can verify

| Environment | Work and evidence |
| --- | --- |
| Linux development machine | Shared Rust model/core/application/protocol, deterministic fixtures, coverage, security and three-peer behavior. Keep the existing desktop tests green. |
| Public GitHub macOS runner | Repeatable iOS Rust/UniFFI compilation, Swift build, simulator unit/UI tests and unsigned simulator artifacts for each relevant change. The existing CI already tests desktop code on macOS, but has no iOS target or app build yet. Pin a supported macOS/Xcode image and record the selected Xcode and Rust versions. Standard hosted runners are [free for public repositories](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). |
| Temporary Apple-silicon Mac | Initial Xcode/SwiftUI/FFI integration, interactive simulator debugging, signing, archiving and TestFlight upload. Use short, planned sessions at exact source commits; avoid making it the only place where builds work. |
| Physical iPhone plus permitted desktop peers | Tailscale routing, foreground inbound listener, TLS identity, clipboard import/copy, cellular/Wi-Fi transitions, background/lock behavior and real multi-computer history. A simulator cannot satisfy this gate. The build Mac need not join the tailnet for these tests. |

The temporary Mac should have a supported macOS/Xcode pair for the test iPhone's iOS version, Apple silicon, preinstalled Xcode or permission to install it, enough storage for Xcode and Rust build products, and reliable SSH or remote desktop access. User-level Rust and XcodeGen installation is sufficient for unsigned simulator builds; administrator access is needed only for host features that require it, such as a system VPN. The build Mac itself does not need Tailscale to compile the app. Plan for at least 16 GB RAM and roughly 100 GB free build space; these are project working targets, not Apple minimums. Verify the chosen pair against [Apple's current Xcode support table](https://developer.apple.com/xcode/system-requirements/) before renting. Pin and check the selected GitHub macOS runner image and Xcode version rather than assuming a moving `latest` label stays fixed ([runner image inventory](https://github.com/actions/runner-images)). A provider with a short billing period and a reliable wipe/rebuild path is preferable; [EC2 Mac Dedicated Hosts have a 24-hour minimum allocation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-mac-instances.html).

## Inputs needed before the first Mac session

1. One physical iPhone with its iOS version known, the official Tailscale app installed and connected to the test tailnet, and permission to install a beta build. A second iPhone is useful later for version coverage, but is not a first gate.
2. An Apple Developer Program team with an available bundle identifier, App Store Connect app record and a team member allowed to sign/upload. For remote installation on a locally held iPhone, choose **internal TestFlight** first; its testers must be App Store Connect users. External testers require a separate beta review path ([Apple TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)). If a registered-device IPA is used instead, prepare device registration/provisioning and a supported local installation path ([Apple registered-device distribution](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices)). Direct Xcode device debugging requires a paired device and Developer Mode; TestFlight installation does not require Developer Mode ([Apple device guidance](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices), [Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device)).
3. One upgraded Linux Shuttli peer for the first connection and a second permitted peer for list/history merging. Use synthetic text and images. Tailnet policy must allow the app connection; check incoming-connection/shields-up policy and any iOS VPN routing rules ([Tailscale incoming policy](https://tailscale.com/docs/features/tailscale-system-policies)). Record environment-specific addresses and evidence only in untracked project memory.
4. Pin Xcode, Rust toolchain, iOS deployment target, bundle identifier, app/SDK/wire versions, test fixtures and release commit. The [iOS spec](ios.md) proposes iOS 16 as a minimum; confirm it against the actual device and selected toolchain in the first build.
5. A plan for private signing material. Keep Apple credentials, certificates, provisioning files, Tailscale keys and clipboard test data out of tracked files, public logs and downloadable CI artifacts. Use synthetic payloads and sanitized diagnostics.

## Staged workflow and stop gates

| Gate | Work | Pass evidence |
| --- | --- | --- |
| 0. Portable preparation | Define the minimal SDK/FFI boundary, wire fixtures and reproducible build scripts in issue #50. Keep existing desktop tests and core coverage green; postpone the full mobile protocol until the real-iPhone network gate passes. | Repeatable baseline CI and a small compilable Rust API for the build spike; no desktop v1 regression. |
| 1. Build spike | Create a minimal SwiftUI target and UniFFI call into the same Rust source. Compile device and simulator libraries, run one native binding test, and build an unsigned simulator app on macOS CI. | Exact-commit CI build and simulator test; no app signing or cloud-host state required to repeat it. |
| 2. Real-iPhone network feasibility | Sign a tiny foreground probe, install it through internal TestFlight or the prepared registered-device path, and connect from a permitted Linux peer. First prove a bounded TCP listener on the Shuttli port over Tailscale, then the Shuttli TLS identity/handshake. Exercise Wi-Fi, cellular, app resume and incoming-policy denial with synthetic traffic only. | Linux can reach and authenticate the foreground iPhone in supported network states; background/lock stops work as designed. If inbound routing fails, investigate Tailscale/iOS conditions and revise the discovery design before building the full UI. |
| 3. Shared protocol and SDK | Land v2 capabilities and current-policy history/list rules, then add phone session lifecycle, per-source roster merge, history list/get/change, foreground cancellation, explicit draft/send and local-copy use cases. Keep capability routing independent of OS type. | Deterministic two/three-peer tests: no roster/history before source permission, all eligible sources send their own snapshot, direct identity verification, no unsolicited phone `OFFER`, no forward loops and truthful partial history. Core production function, line and region coverage each remains strictly above 95%. |
| 4. Native app | Implement Home, History, detail, Devices and Settings. Simulator tests cover navigation, localization, permission states, lifecycle callbacks and bounded previews. | CI simulator tests and interactive review on the temporary Mac; no simulated clipboard result is counted as physical paste evidence. |
| 5. Real-device acceptance | Run the [iOS acceptance matrix](ios.md) with a signed exact-commit build: explicit text/image import and send, cross-app paste after explicit Copy, two-computer history merge, source permission changes, reconnect/eviction, lock/background, old peer and malformed content. | OS readback/cross-app paste and source-specific outcomes from the real iPhone and desktop peers; no body/thumbnail in system notifications or diagnostics. |
| 6. Beta package | Archive, validate, upload and install an internal TestFlight build; verify upgrade keeps identity/policy and clears session content as specified. | Traceable commit, Xcode/Rust/SDK/wire versions, archive checksum, installation and upgrade result. App Store publication is a separate release decision. |

The first paid Mac session should complete gate 1. Gate 2 follows only when a signing and installation path is available. Prepare source, scripts, test fixtures and app identifier before starting it. Keep an exact build/run log with toolchain versions and synthetic failure categories. Subsequent code changes should use the hosted macOS CI; rent another interactive session only for Xcode-specific debugging, visual review, signing or archive work.

## Cloud-Mac session hygiene

- Start from a clean checkout of an exact commit. Confirm Xcode path/version, Rust targets (`aarch64-apple-ios` and `aarch64-apple-ios-sim`), simulator runtime and available build space before compiling. Capture commands in repo scripts once proven so a new Mac can reproduce them.
- Use an isolated login/keychain for project signing. Prefer narrowly scoped, revocable credentials over a personal primary Apple login. Never store signing material in the repository or an unprotected build cache. Allow beta upload only from a protected branch or deliberate release workflow.
- The cloud Mac normally needs GitHub and Apple services, not access to personal clipboard peers. If remote access through Tailscale is necessary, give the host a short-lived, narrowly scoped node identity; remove it when the session ends ([Tailscale ephemeral nodes](https://tailscale.com/docs/features/ephemeral-nodes)).
- Before releasing the host, upload only source-independent build reports and sanitized test artifacts, revoke temporary access, remove signing keys and profiles, and wipe the workspace. Keep private device names, addresses, UDIDs and test logs outside the public repository and issues.

## Open decisions before implementation

- Confirm the physical iPhone/iOS version and Apple Developer Program/App Store Connect access. Without a signing/distribution path, simulator work can proceed, but gate 2 cannot be completed from a remote Mac.
- Select the short-term cloud Mac provider and exact supported Xcode image after the phone version is known. The permanent CI target can be chosen independently.
- Verify the iOS foreground inbound listener over the separately installed Tailscale VPN early. That result decides whether the current desktop-assisted discovery contract is implementable as written.
